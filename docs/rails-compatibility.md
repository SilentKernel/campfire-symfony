# Rails compatibility

The Symfony app and the Rails image can take turns on the same storage volume in either
direction. This page describes every format they share and how each one is reproduced. The
implementations are in `src/Rails/` (no framework dependency), `src/Http/`, `src/Database/` and
`src/Storage/`. They are tested against vectors generated by Rails itself.

Everything below assumes both apps use the same `SECRET_KEY_BASE`.

## Key derivation

`Rails\KeyGenerator` is `Rails.application.key_generator`: PBKDF2-HMAC-SHA256, 1000 iterations,
over `SECRET_KEY_BASE` (`load_defaults 7.0+`). Keys are derived once per process and cached by
salt and length.

| Salt | Length | Used for |
|---|---|---|
| `signed cookie` | 64 | signed cookies (HMAC-SHA1) |
| `authenticated encrypted cookie` | 32 | encrypted cookies and the session (AES-256-GCM) |
| `active_record/signed_id` | 64 | `signed_id` / `find_signed` |
| `signed_global_ids` | 64 | SGIDs |
| `turbo/signed_stream_verifier_key` | 64 | Turbo signed stream names |
| `ActiveStorage` | 64 | blob signed ids, variation keys, disk URLs, direct-upload tokens |

## Cookies

`Rails\RailsCookies`, `Http\Cookies`, `Http\RailsSession`, `Http\Flash`:

| Cookie | Kind | Contents | Options |
|---|---|---|---|
| `session_token` | signed, permanent | the `sessions.token` | `httponly`, `samesite=lax`, `path=/`, expires in 20 years; re-set on every authenticated request |
| `_campfire_session` | encrypted (the cookie session store) | JSON object: `session_id` (`SecureRandom.hex(16)`), `_csrf_token`, `return_to_after_authenticating`, `flash` | `httponly`, `samesite=lax`, expires in 20 years (`expire_after: 20.years`), rewritten on every request that loads it or carries a session id |
| `last_room` | plain, permanent | a room id | `samesite=lax`, expires in 20 years |

**Formats (Rails 8.2, `load_defaults 8.2`):**

- Values are serialized as JSON (`cookies_serializer :json`, ActiveSupport::JSON escaping).
  Marshal-dumped values are refused, as Rails' `:json` fallback serializer refuses them.
- **Signed:** `Base64.strict(<envelope>)--<hex HMAC-SHA1>` (`MessageVerifier`).
- **Encrypted:** `Base64(ciphertext)--Base64(12-byte IV)--Base64(16-byte auth tag)`, AES-256-GCM
  with empty auth data (`MessageEncryptor`).
- **Envelope:** the cookie jars use the legacy dual-serialized metadata envelope:
  `{"_rails":{"message":"<strict Base64 of the JSON value>","exp":"2046-01-01T12:00:00.000Z","pur":"cookie.<name>"}}`.
  `exp` is ISO 8601 with milliseconds in UTC, or `null`. `pur` is always `cookie.<name>`.
- **Reading** tries purpose `cookie.<name>` first, then no purpose. This is Rails' fallback for
  pre-5.2 cookies.
- **Expiry:** a value is expired when `now >= exp`. Permanent cookies use `20.years.from_now`
  for both the envelope and the `expires` attribute.
- **Wire format:** `Rack::Utils.escape` on the way out (`URI.encode_www_form_component`: a space
  is `+`, and `*-._` and alphanumerics stay). `Rack::Utils.unescape` on the way in; a malformed
  `%` escape leaves the value untouched. When a name repeats in the `Cookie` header, the first
  occurrence wins.
- **Set-Cookie attributes** follow Rack's order: `path`, `max-age`, `expires`, `secure`,
  `httponly`, `samesite`.
- **Secure flag:** unless `DISABLE_SSL`, every cookie gets `; secure` and responses carry HSTS
  `max-age=63072000; includeSubDomains`, as with `ActionDispatch::SSL`.
- **Deletion:** `cookies.delete` sends an empty value with `max-age=0` and the 1970 date, and only
  for a cookie the request actually sent.

**Session semantics** (`Rack::Session::Abstract::PersistedSecure` + `CookieStore`):

- Reading the session loads the cookie only if it has a `session_id`. Writing always loads it,
  creating an id when there is none.
- `reset_session` clears the data and issues a new id.
- The flash is stored as `{"discard": [...], "flashes": {...}}` under `flash`. A flash set by one
  runtime is shown and consumed by the other.

## CSRF

`Rails\CsrfToken`, `Rails\ForgeryProtection`, `Http\Csrf`, as configured by Campfire:
`protect_from_forgery with: :exception`, per-form tokens, origin check, token in the session.

- **The secret** is `session["_csrf_token"]`: `SecureRandom.urlsafe_base64(32)`, created on first
  use.
- **The global token** is `HMAC-SHA256(real, "!real_csrf_token")`. It goes in
  `<meta name="csrf-token">`.
- **Per-form tokens** are `HMAC-SHA256(real, "<normalized action path>#<method>")`. Each
  `button_to`/form gets one. Relative actions are resolved against the page path, and a trailing
  `/` is dropped.
- **Masking:** pages get tokens masked, as a fresh 32-byte one-time pad followed by
  `pad XOR token`, in URL-safe Base64 without padding.
- **Verification:**
  - GET and HEAD pass.
  - Otherwise the `Origin` header must be absent or equal `request.base_url`. `Origin: null` is
    rejected.
  - Then `params[:authenticity_token]` or `X-CSRF-Token` must unmask to the global token, the
    real token, or the per-form token for this path and method. The unmasked real token is also
    accepted.
  - Failure is a 422 (`InvalidAuthenticityToken`).
- **Not used:** the reference's Rails version (8.2.0.alpha) has no `Sec-Fetch-Site` strategy, so
  none is used here either.

The cross-runtime check confirmed that a page rendered by one app, with its meta token and its
per-form tokens, posts successfully to the other app.

## Signed ids, SGIDs, Turbo stream names

| What | Format |
|---|---|
| `user.signed_id(purpose: :avatar)` (avatar URLs `/users/<token>/avatar`), `purpose: :transfer, expires_in: 4.hours` (session transfer links) | Generated with HMAC-SHA256, `::JSON`, URL-safe Base64 without padding (`use_legacy_signed_id_verifier: :generate_and_verify`). Read with that, falling back to SHA1 + strict Base64. Purpose `user/avatar`, `user/transfer`. |
| Mention SGIDs (`attachable_sgid`) | `GlobalID::Verifier`: HMAC-SHA1, URL-safe Base64 **with** padding, `{"_rails":{"data":"gid://campfire/User/1?expires_in","pur":"attachable"}}`, no expiry. Rails 7.0 legacy envelopes and pre-1.0 self-validated SGIDs are read too. As in `lib/rails_ext/action_text_attachables.rb`, a User SGID with a bad signature (after a key rotation) still resolves. |
| Turbo signed stream names | `MessageVerifier` with SHA256 and `JSON`, strict Base64, **no** envelope. The name is the stream's parts joined with `:`. Records are `to_gid_param` (`gid://campfire/Rooms::Open/1`, URL-safe Base64), so a room's message stream is `<room gid param>:messages`. |
| Active Storage | `Rails.application.message_verifier("ActiveStorage")`: SHA1, strict Base64, `{"_rails":{"data":…}}`. Blob signed ids use purpose `blob_id` and never expire (Campfire leaves `urls_expire_in` unset). Variation keys use `variation`, disk URLs `blob_key` (5 minutes), direct uploads `blob_token`. |

Every stream name the app uses is listed in [realtime.md](realtime.md).

## Database

- **Schema.** `db/schema.sql` is the reference database's `sqlite_master` DDL, including the
  FTS5 `message_search_index` (porter tokenizer) and its shadow tables. On empty storage,
  `campfire:install` loads it and then writes what `db:schema:load` writes:
  - the 15 versions of `db/versions.json` in `schema_migrations`;
  - `environment=production` and `schema_sha1` (the SHA1 of the reference `schema.rb`) in
    `ar_internal_metadata`.

  The result is byte-identical to a Rails-created database, and Rails' `db:migrate:status` is
  clean on it. A database with a missing version is refused: boot the Rails image once to
  migrate it.
- **Doctrine never alters the schema.** The `message_search_index` tables are excluded from the
  schema tool (`schema_filter`). The job queue is a separate database file.
- **Datetimes** are UTC text exactly as Active Record writes them: `2026-03-02 16:00:00.123456`.
  Microseconds appear only when non-zero (`rails_datetime` DBAL type). Queries must bind times
  with this type, so text comparisons such as `created_at < ?` order correctly against rows Rails
  wrote. Rows written by `insert_all` get SQLite's `STRFTIME('%Y-%m-%d %H:%M:%f', 'NOW')`, as in
  Rails.
- **Other column formats:**
  - Enums are stored as Rails stores them (`role`, `status` as integers; `involvement` as
    strings).
  - The STI `type` column holds `Rooms::Open`, `Rooms::Closed` or `Rooms::Direct`.
  - Direct rooms have a `NULL` name.
  - Passwords are bcrypt `$2a$12$`.
  - Session and bot tokens are `has_secure_token`'s 24-character base58.
- **Search.** The FTS row is written after commit, as `after_create_commit` does. A crash between
  the commit and the index write leaves a message out of search, in Rails and here alike.

## Active Storage

- **Blobs:**
  - Keys are `SecureRandom.base36(28)`.
  - Files live at `files/<key[0,2]>/<key[2,2]>/<key>`.
  - `checksum` is the Base64 MD5 of the bytes.
  - `service_name` is `local`.
  - `metadata` is the JSON Rails' analyzers write (`identified`, `analyzed`, `width`/`height`,
    video `duration`, …). Analysis runs as a job, as Rails does. Message attachments are
    analyzed and processed synchronously, as `process_attachment` does in Rails.
- **Variants** are tracked (`active_storage_variant_records`). `variation_digest` is
  `Base64(SHA1(Marshal.dump(transformations)))`, computed with a Ruby Marshal writer that keeps
  Symbol vs String (`format: :webp`). The variant image is attached to the record as `image`.
  The named variants are:
  - message `:thumb`: `resize_to_limit [1200, 800]`;
  - avatar `:square`: webp, 512²;
  - account logo `:large` (png, 512²) and `:small` (png, 192²);
  - video posters: `preview(format: :webp, resize_to_limit: [1200, 800])`, from the first frame
    ffmpeg selects with Rails' `video_preview_arguments`, stored as `preview_image`.
- **Processing** makes the same libvips calls as image_processing/ruby-vips: `autorot`,
  `thumbnail_image(..., size: :down, no_rotate: true)`, then a sharpen convolution. With libvips
  8.16.1 (Debian trixie, as in the Rails image) variants are byte-identical. ffmpeg 7.1.5 posters
  are byte-identical to the seed's.
- **MIME detection** uses Marcel's tables, dumped from the gem (`src/Storage/Marcel`).
- **URLs** follow Rails' routes and signing: `rails/active_storage/{blobs,representations}/
  {redirect,proxy}/…` and `disk/:encoded_key/*filename`.

The cross-runtime check uploaded the same PNG through both apps. It got identical blob metadata,
the same variation digest and a byte-identical thumbnail.

## Switching runtimes

Both directions were tested on one Docker volume with `tools/crossruntime/`: 375 checks, 0
failures. See the [report](internal/crossruntime-report.md).

**Rails → Symfony.** Stop the Rails container. Start this image with the same `SECRET_KEY_BASE`,
VAPID keys and volume.

- `campfire:install` sees an up-to-date schema and leaves it alone.
- Signed-in users stay signed in. Open tabs keep posting with the CSRF tokens Rails rendered.
- Flash and `return_to` survive the switch.
- Queued Resque jobs that hadn't run are not carried over; Rails' Redis is inside its container.

**Symfony → Rails.** Stop this container. Start the Rails image on the volume.

- Rails' `db:prepare` finds every migration applied.
- Sessions, uploads, variants and search rows written here are used as they are.
- `jobs.sqlite3` and the `caddy/` directory are ignored.
- A database created by Symfony from empty storage is accepted too.

**Both at once** works for a short switch-over. SQLite arbitrates writes (`BEGIN IMMEDIATE`, 5 s
busy timeout), and presence is shared through `memberships`. Live broadcasts don't cross: each
runtime has its own pub/sub.

**After a crash** of either app, the other one takes over. Every acknowledged write is there.

## Golden vectors

`tests/vectors/*.json` are copied unchanged from once-campfire-rust (`vectors/`, MIT). They were
generated by the reference app in production mode inside the `campfire-reference` image, with the
parity `SECRET_KEY_BASE` and the clock frozen at 2026-01-01T12:00:00Z.

| File | Contents |
|---|---|
| `rails_compat.json` | key generator, cookie escaping, signed/encrypted cookies, session, CSRF, signed ids, GlobalIDs, SGIDs (verified and unverified), Turbo stream names, app verifiers, passwords |
| `storage.json`, `storage/` | verifier outputs, disk URLs, variations and digests, Marcel cases, filenames, analyzer metadata, and expected variant/preview bytes for the fixture images and video |
| `campfire_routes.json` | route recognition and generation |
| `campfire_sessions.json` | the seed's session cookies, blob signed ids and a forged cookie |
| `campfire_user_agents.json` | browser detection and the `allow_browser` gate |
| `ruby_core.json` | Ruby string, integer and float behaviour, HTTP byte ranges |

Tests read them in place. Never edit them. To regenerate, use the Rust checkout's tools (they
need Docker and the reference image), then copy the files into `tests/vectors/`:

```sh
cd .cache/once-campfire-rust      # or $BENCH_HOME/once-campfire-rust
reference-tools/run.sh reference-tools/rails_compat_vectors.rb   # vectors/rails_compat.json
reference-tools/run.sh reference-tools/ruby_core.rb              # vectors/ruby_core.json
reference-tools/storage/run.sh                                   # vectors/storage.json, vectors/storage/
```

Two other fixture sets are generated here, by Rails in the `campfire-reference:app` image:

- `tests/fixtures/richtext/`:
  - `run.sh` writes `canonical.json`: what Action Text stores and renders for each body of the
    Rust port's corpus.
  - `run_seed.sh` writes `seed.json`: the seed messages rendered by Rails.
- `tests/fixtures/rails/`: compiled assets, importmap/stylesheet tags and two reference layouts.
